Drive the pull request described above to merge-ready by running the /iterate loop.
You are the orchestration loop: poll each verification layer, fix code, push, and
re-poll — you only stop when every *present* layer is green, or a genuine blocker
requires a human.

## Environment

- `GITHUB_TOKEN` is exported in the environment; authenticate `gh` with it
  (e.g. `echo $GITHUB_TOKEN | gh auth login --with-token`) if not already authenticated.
- The repository is NOT pre-cloned. Clone it yourself, check out the PR's head branch,
  and create a short-lived local work branch off it for any edits you push:
  `git clone https://github.com/{full_name}.git`, then
  `git fetch origin pull/{number}/head:pr-branch` or `git checkout {head_ref}`.
- Never commit to `main`/`master`; push fixes only to the PR's head branch.

## Discover which verification layers this repo actually has

Run `gh workflow list --json name -q '.[].name'` and `.github/workflows/*.yml` to see
what is configured. A "present" layer means one of:
- **CI checks** — `gh pr checks` returns results.
- **Automated PR review** — an `all-hands-bot`/`openhands` review or a workflow like
  `pr-review` / "PR Review" exists. When branch protection requires approval, request
  `all-hands-bot` and keep iterating until it returns `APPROVED`.
- **QA bot** — a workflow like `qa-changes` / "QA" exists.

Your "all passed" condition is: every *present* layer is green on the current head SHA.
Do not block on layers that don't exist. Also check for any existing unresolved review
threads right away — open pending feedback must not be missed. A missing approval is not
a human blocker while `all-hands-bot` can be requested or re-requested.

## The loop

0. **Resolve merge conflicts first.** Before evaluating CI/reviews, check whether GitHub
reports the PR as conflicting or dirty. If so, fetch the base branch, merge or rebase
it into the PR head branch, resolve conflicts carefully, run relevant checks, and push
to the PR head branch. Never leave a known merge conflict untreated.
1. Poll every present layer (see below).
2. If the PR is a draft, complete all fixable implementation, testing, CI, description,
and review-thread work. Once it is genuinely ready for human or automated review, run
`gh pr ready` yourself. Draft status is not a reason to request human approval.
3. If a fix is needed, make the minimal fix, commit, push to the PR head branch,
   re-request review from the review bots (`gh pr comment`, and request
   `all-hands-bot`/`openhands` reviewers via the GitHub API), then go back to 1.
4. If a layer is still pending, sleep ~60s and re-poll (back off exponentially to a
   1h cap when green-but-waiting; reset whenever anything changes).
5. If CI turns all-green for the current SHA, that is worth one celebratory log line,
   then continue watching the other layers.

## How to read each layer

- **Mergeability**: `gh pr view --json mergeable,mergeStateStatus`. `CONFLICTING` or `DIRTY` means the base branch must be synchronized before the PR can be green.
- **CI**: `gh pr checks --json name,state,bucket -q '...'`. Zip failed==0 and
  pending==0 ⇒ green. Inspect failures with `gh run list --commit <sha> --status
  failure` and `gh run view <id> --log-failed`.
  - *Branch-related* (fix the code): compile/lint/typecheck in files you touched,
    deterministic test failures in changed areas, snapshot/static-analysis violations.
  - *Flaky/unrelated* (rerun, max 3 reruns per SHA): network/DNS/registry timeouts,
    runner provisioning failures, infra errors, non-deterministic failures in code you
    didn't touch. If ambiguous, inspect logs once before choosing.
- **Review**: `gh pr view --json reviews,reviewRequests,reviewDecision` — filter to
  reviewers (OWNER/MEMBER/COLLABORATOR or `openhands`/`all-hands-bot`). An approval
  from `all-hands-bot` satisfies an independent-review gate. If approval is absent,
  request or re-request `all-hands-bot`, wait for its response, address every
  actionable finding, push fixes, resolve its threads, and request it again until
  it returns `APPROVED`. `CHANGES_REQUESTED` means continue that loop; `COMMENTED`
  means inspect and address actionable feedback. List inline comments with
  `gh api repos/{full_name}/pulls/{number}/comments`.
- **QA**: `gh api repos/{full_name}/issues/{number}/comments` — a comment containing
  `Status: PASS` ⇒ passed; `FAIL`/`PARTIAL` ⇒ fix per the report.

## Review comment handling

For every actionable review thread: fix the code, commit, push, then reply to the
thread referencing the commit SHA, and resolve the thread via the GitHub GraphQL API.
For non-actionable or already-addressed comments, reply briefly and resolve. Do not
leave threads dangling. Before finishing, verify zero unresolved threads remain.

## Stop conditions

A live PR may only be left in one of two states:

1. **Merge-ready** — every *present* verification layer is green on the current head
   SHA, with zero unresolved review threads. Then report success and stop.
2. **Genuinely blocked on a human** — you cannot make it merge-ready because the
   blocker is something only a person can resolve. Then leave **exactly one** short
   comment on the PR that contains the phrase `needs human approval` (verbatim, in
   its own sentence), state briefly what you did and what is needed from a human, and
   stop. Do not also post a `[iterate-watchdog] block:` comment.

Blockers that warrant `needs human approval` include: permissions you lack, an
infrastructure/CI outage, a flaky failure that survived your 3-rerun budget,
ambiguity that cannot be resolved safely, a design/scope call, protected human-authored
content, or a review decision that `all-hands-bot` explicitly cannot make.

**Never** post `needs human approval` for a missing independent approval, a pending
review request, `REVIEW_REQUIRED`, or an `all-hands-bot` `COMMENTED`/
`CHANGES_REQUESTED` response. Request or re-request `all-hands-bot`, address its
feedback, and continue until it approves. More generally, never stop loop-ending for
anything an AI can resolve: push fixes, rerun flaky jobs (up to 3 per SHA), resolve
threads, and re-request review until a true stop condition. The marker is only for a
genuine human-gated blocker. The watchdog resumes after a new commit or human reply.

There are two further legitimate endings:
- The PR is merged or closed — stop.
- You are still making progress but approach your turn/time limit — stop with a terse
  status note on the PR (no marker; a later run and/or a new head SHA resumes it).

Pushing a fix is NOT a stop condition — keep going. Do not ask the user whether to
continue; act autonomously until a stop condition is met.

## Output

End your final message with a terse summary:
PR status (green / blocker reason), how many fixes you pushed, how many review threads
you resolved, and the remaining failures or comments (or "none").
